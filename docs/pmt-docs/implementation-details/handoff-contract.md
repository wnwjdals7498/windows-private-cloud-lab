# 기능 인계 규약

인계의 단위는 **기능의 행동과 검증 가능한 결과**다. 어느 파일을 얼마나 수정했는지를 성공 기준으로 사용하지 않는다. [상세계획 안내](README.md)

## 인계에 반드시 들어갈 내용

| 항목 | 기록할 내용 | 누락 시 생기는 문제 |
| --- | --- | --- |
| 목적 | 사용 주체의 어떤 문제를 해결하는가 | 구현자가 목적 없이 구조를 바꿈 |
| 추가/수정/삭제 범위 | 새 행동, 기존 행동의 의미 변화, 종료할 경로. 대상 데이터의 처리 범위는 별도 | 의도하지 않은 기능·삭제가 섞임 |
| goal | 외부 관찰 결과·불변식·성공 판정 | 파일 변경이 완료로 취급됨 |
| non-goal | 제외 기능·환경·역할·다른 소유자 | 여러 에이전트가 같은 책임 구현 |
| 책임 | 카드 ID·모듈 소유자·원래 P 작업·공유 계약 | 변경 충돌·누락 |
| 기준선 | 검토된 계약/코드 revision·설정/fixture/schema version·게이트 상태 | 서로 다른 타입·의미를 구현 |
| input 의미 | 이름·업무 의미·원천·권위·필수성·단위·유효성·신뢰 경계 | 같은 필드를 서로 다르게 해석 |
| output 의미 | 이름·업무 의미·생산자·소비자·발생 시점·부재/실패 표현 | 접수·완료·미관측 혼동 |
| 동작 | 준비→검증→접수/실행→관측→결과·감사→인계 흐름 | 부작용·원자성·재시도 누락 |
| 실패/복구 | 실패 지점·남는 상태/자원·안전한 재개·수동 조치 | 재실행 때 중복 생성·데이터 손실 |
| Test | 조건·자극·기대 결과·독립적인 확인 대상 | 구현을 따라 쓰는 자기 검증 |
| Logging | event의 의미·상관 필드·분류·저장·마스킹·대조 시험 | 로그가 있어도 복구/판정 불가 |
| 완료 증거 | 실행한 검증·실제 결과·artifact·미검증·한계 | fake 성공을 실환경 성공으로 오인 |
| 다음 소비자 | 넘길 계약·상태·시험 결과·남은 게이트 | 다음 작업이 잘못된 선행을 사용 |

input/output의 직접 값은 실행 환경 설정이나 시험 fixture에서 관리한다. 기능 인계에는 실제 주소·계정·사양·예시 ID를 복사하지 않는다. 필드명·상태 이름·단위의 정의와 고정된 사용자 규모는 의미를 설명하는 계약이며 임의 예제 값과 구분한다.

## 서브에이전트에 전달할 요청 구성

1. 해당 카드의 행동 범위·goal·non-goal을 전달한다. 여러 카드일 때 완료 순서와 중간 인계를 지정한다.
2. 현재 계약 기준선·공유 인터페이스의 소유자·승인된 게이트·코드/실호스트 권한을 전달한다.
3. consumer가 사용할 output 의미와 provider에 넘길 input 의미를 확인하게 한다.
4. 정상·거부·중복·실패/복구 Test 및 Logging의 확인 방법을 준다.
5. 독점 책임 모듈·공유 변경 요청 절차·통합 시점을 지정한다.
6. 완료 보고 형식과 실행하지 못한 항목을 어떻게 남길지 정한다.

수정 경로는 충돌 방지를 위한 보조 메타데이터로만 둘 수 있다. 특정 경로의 편집을 강제하지 않고 필요한 위치는 [구조](../architecture.md)와 모듈 책임에 따라 구현자가 정한다. 공유 계약·배포 설정·migration을 다른 책임과 동시에 고치지 않는다.

## Test 작성 규칙

각 테스트는 준비 조건→자극→기대 행동→검증 증거를 갖는다. 로그 메시지 한 줄이나 HTTP 성공만으로 부작용 완료를 판정하지 않는다. DB 제약·실제 자원·읽기 결과·계약 fixture 등 독립적인 관측을 사용한다.

필수 분류는 정상, 잘못된/권한 없는 입력, 동일 요청 반복·동시 요청, 중간 실패·응답 유실·재시작, 복구 후 재실행이다. 적용할 수 없는 분류는 이유를 적고 억지 시험을 만들지 않는다. 정책 함수·DB·프로세스·TLS·제품 실호스트 시험을 구분한다.

## Logging 작성 규칙

event 이름만 나열하지 않고 어떤 사실을 언제 기록하는지 적는다. 어떤 요청·작업·실행·제품 Job·VM·통지와 연결할지, 진단/원장/감사/증거 중 어디에 보존할지, 누락·중복·순서 역전 때 어떻게 대조할지를 포함한다. 전체 입력/비밀/실제 접속정보를 기록하지 않는다.

log 시험은 필요한 event의 존재·상관 관계·허용 필드·비밀 부재·관측 시각·원장 일치·저장 장애 대응을 검사한다. 실제 행위를 확인하지 않고 기대 로그만 출력하는 구현을 성공으로 판정하지 않는다.

## 서브에이전트 완료 보고

| 항목 | 필요한 내용 |
| --- | --- |
| 대상·기준선 | 카드·공유 계약·구현 revision·승인된 범위 |
| 결과 | 어떤 입력 의미에 어떤 관찰 행동을 구현했는가 |
| 범위 차이 | 추가/수정/삭제 행동 중 수행·미수행·범위 밖 발견 |
| Test 증거 | 조건·명령/절차·종료 결과·기대/실제·자료 위치 |
| Logging 증거 | event·상관·원장 대조·마스킹·저장 장애 확인 |
| 복구 | 실제 확인한 실패 지점·남은 자원·재개 가능 여부 |
| 통합 영향 | 공유 계약 변경 요청·DB migration·의존 소비자 |
| 미검증 | host/선택/외부 인계 부재와 다음 필요한 증거 |

단순히 ‘완료’·‘파일 작성’·‘테스트 추가’라고만 보고하지 않는다. 주 에이전트는 실제 diff·검증 결과와 계약을 대조한 뒤 준비도를 판정한다.
