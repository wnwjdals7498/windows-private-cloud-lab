# GPT-6 Luna 병렬 실행 계획

**주 에이전트 한 명이 계약·통합·실호스트 실행을 관리하고, GPT-6 Luna 서브에이전트를 최대 세 명씩 배정한다.** 여기서 ‘6 Luna’는 모델 `gpt-6-luna`를 뜻한다. 작업 수가 늘면 같은 역할의 다음 카드를 순차 배정한다. 서브에이전트 수를 기능 수만큼 늘리지 않는다.

현재 세 영역 상세계획 작성에 이 구성을 사용했다. 아래는 향후 실제 구현 때 적용할 배정안이며 지금 VM·코드 구현을 실행했다는 뜻은 아니다. [인계 규약](handoff-contract.md)

## 1. 역할

| 역할 | 책임 | 독자적으로 바꾸지 않는 것 |
| --- | --- | --- |
| 주 에이전트 | 사용자 결정·PMT·계약 기준선·작업 배정·공유 변경·통합·실호스트 실행권·완료 판정 | 미승인 G 게이트를 통과 처리하지 않음 |
| Luna A — 실행/제품 | Hyper-V/VMM·이미지·bridge의 실제 실행 의미·VM 변경·재조회 | Cloud 계약·공통 상태 enum·소유권 DB |
| Luna B — 서비스/원장 | 접수·멱등·저장·Worker·조회·통지·경합 | 제품 실행을 직접 endpoint에 넣거나 provider 독자 수정 |
| Luna C — 인프라/운영·검증 | 호스트·AD·Storage·Cluster·이관·진단·증거·독립 시험 | 다른 모듈 상태 원장·공통 schema·실호스트 무단 변경 |

역할은 영구적인 모듈 소유가 아니다. 각 배정마다 카드의 책임 행동·소비 계약·배타 범위를 정한다. 인접 작업이 같은 모듈을 바꾸면 한 담당자에게 이어서 맡기거나 순차 통합한다.

## 2. 먼저 끝낼 공유 기준선

F01→F02→F03의 계약 정의를 주 에이전트와 한 담당자가 통합한다. 다른 담당자는 독립 fixture 검토·누락 검토를 할 수 있지만 같은 공유 정의를 동시에 변경하지 않는다.

공유 기준선은 [SC01~SC08](shared-contracts.md)의 입력/출력 의미·필수성·오류·버전·상태·소유권·transaction·복구 불변식과 검증 fixture를 포함한다. 아직 필요한 G04/G06 선택은 ‘미정’으로 남긴다. 새 구현은 해당 선택이 필요한 범위 직전에 멈추고, 선택에 독립적인 계약·순수 정책·시험 설계는 진행할 수 있다.

## 3. 코드 개발과 실호스트 실행은 다른 순서다

기존 P 순서는 **실제 완료 증거의 의존성**이다. 예를 들어 이미지가 실제로 준비되기 전에도 이미지 manifest 검증과 잘못된 입력 거부 정책은 독립 fixture로 개발할 수 있다. 그러나 그 결과로 P04 이미지 복제나 P05 실제 생성이 끝났다고 표시하지 않는다.

| 상황 | 병렬 가능한 작업 | 기다려야 하는 작업 |
| --- | --- | --- |
| 제품 호스트 미준비 | 순수 정책·명시적 fake·독립 계약·읽기/변경 계획 검사 | 제품 모듈 실호출·VM 생성·성능 판정 |
| G04 기술 미정 | 신원·접수·저장 의미·오류·fixture 설계 | 특정 IIS/런타임/영속 provider를 승인안으로 구현·배포 |
| G06 조회 대상 미정 | 조회 DTO 의미·신선도·권한/오류 시험 설계, 두 후보의 제한된 비교 시험 | 실제 소비 조회 객체·SQL 권한·Cloud adapter 고정 |
| Cloud 실제 서비스 미준비 | 승인 계약 test double·outbox/replay·parser 대조 | X01~X04 실제 공동 인수 |
| 같은 실호스트 사용 | 코드·정적·독립 단위/계약 시험 | 네트워크·AD·클러스터·모드·인증서·VM 변경 동시 실행 |

fake/모의 환경에도 mode·신원·자원 namespace를 분리한다. shared SQL schema·migration·fixture 원본도 한 담당자만 변경한다. mock과 실환경을 조용히 바꾸는 fallback은 금지한다.

## 4. 코드 준비용 병렬 묶음

아래는 카드 전체 완료 순서가 아니라 **배정할 하위 행동**이다. 각 묶음 종료 후 공유 변경을 직렬 통합한다. 필요한 계약/게이트가 없으면 해당 열은 ‘설계·검토만’으로 제한하고 다른 열을 진행한다.

| 묶음 | 시작 조건 | Luna A | Luna B | Luna C | 통합 장벽 |
| --- | --- | --- | --- | --- | --- |
| D0 | 최신 설계·P 계획 확인 | F01 의미·strict 계약 정의 | 동일 계약의 독립 consumer 기대값 검토 | F02/F03 설정·증거 요구 검토 | 주 에이전트가 F01→F02→F03 기준선 확정. 공유 정의의 작성자는 한 명 |
| D1 | SC01/02/07 의미 고정 | F07/F08 이미지·VM 정책·관측 port의 독립 검증 | S03 접수·멱등·transaction 의미와 경합 fixture | F04/F05 읽기 점검·예산·네트워크 계획 검사 | 순수 정책·fixture 검증, 실제 생성/네트워크 변경 미완료 |
| D2 | D1 계약. B의 저장 provider와 C의 서비스 기술 의존 범위만 G04 필요 | F06/F07/F08의 직접 Hyper-V adapter 후보·이미지 초기화 검증. 해당 G01~G03/G08·P 선행 적용 | S03 선택 저장 provider의 원자적 접수·고유성 구현 | S02 인증/인가 정책·S05 최소 진단/제한의 독립 검증. 실제 인증서는 G05 적용 | 실제 provider 경쟁·실행 adapter·신원 검증 결과 대조. 공통 API 조립은 root. A를 서비스 기술 선택 때문에 대기시키지 않음 |
| D3 | S03 저장·SC03 bridge 계약 준비 | S04 중 bridge/프로세스 경계, 이후 실행 provider 연결 | S04 중 Jobs 점유·제출 의도·재개 정책, S05 접수 조립 | F09/F10 설치 사전검사·역할 설정·운영 계정 계획 | bridge와 Jobs는 서로의 소유 범위를 수정하지 않음. 통합 후 중단/재시작 계약 시험 |
| D4 | VMM 계약·필요 G06 선택 또는 제한된 비교 시험 | S06 VMM 실행·관측 adapter·이전 검증 | S07 읽기 객체, 이어 S08 완료 저장/전달 | O01~O04 Storage·Compute 클러스터 운영·장애 시험 설계 | 실제 VMM/SQL/Cluster 증거는 원래 실호스트 순서에서 확보 |
| D5 | 실행·관측·통지 계약 통합 | S10~S12 전원·삭제·자원 변경 정책과 adapter 시험 | O05~O07 유지보수·이관·Cloud 인계의 조정 로직 | O08~O11 운영 관측·복구·인증서·자원 고갈 시험 | B는 binding port 소비만. A 소유 정책·공유 mapping 수정은 요청 후 root 통합 |
| D6 | 전체 계약·해당 코드 검증 결과 | S09 신청→실행→접근 공동 시험의 Windows 준비 | O12~O14 버전·재현·복원·인수 절차 검증 | 독립 계약·로그/원장·민감정보·실측 한계 검토 | 실측 없이 공동 인수 완료 처리 금지 |

이 표는 조기 개발 가능한 작은 행동을 지정한다. 예를 들어 D2의 S05 진단 정책은 S04 실동작을 완료시키지 않는다. D5에서 S12 변경 정책을 먼저 만들었어도 최종 P15 충돌 시험은 S11 삭제 결과 뒤에 한다. 동일 카드 안의 역할 분담은 API/port 의미와 작성 책임을 먼저 고정하며 중복 구현하지 않는다.

## 5. 실제 환경의 통합·완료 순서

실호스트 변경 실행권은 항상 한 명에게 있다. 서로 다른 VM을 건드리더라도 같은 물리 호스트·네트워크·디스크·자원 예산을 공유하므로 기본 직렬 실행한다. 코드 시험은 별도 격리 자산으로 병행 가능하다.

| 검증 묶음 | 완료 순서 | 배타성·통과 증거 |
| --- | --- | --- |
| V0 | F01→F02→F03→F04→F05 | 계약·실측 환경·네트워크 게이트 |
| V1 | F06→F07→F08, F09는 F05 뒤 독립 착수 | Compute/이미지/직접 작업과 AD의 의존은 별개. 실제 변경은 직렬 |
| V2 | S01→S02→S03→S04→S05 | G04/G05와 초기 IIS·영속성·중복/복구 검증 |
| V3 | F10 | VMM/SQL 설치·Compute 편입·실제 제품 명령 |
| V4 | S06→S07→S08 및 O01→O02→O03→O04 | 논리상 두 경로 병행 가능. G06/G07, 실제 자원 변경은 예약 후 직렬 |
| V5 | O05→O06 | 두 V4 경로 완료, 데이터 보존 이관·추가 노드 정지·재부팅 |
| V6 | O07 | X01/X02/X03, Linux8 별도 검증과 서비스4+4 |
| V7 | S09 | X04 포함 실제 회원 신청·소유권·VM·SSH |
| V8 | S10→S11→S12 | 전원→삭제→자원 변경/전체 충돌·실제 사양 |
| V9 | O08→O09→O10→O11 | 관측·재시작/통지 복구·인증서·자원 고갈·관리자 인계 |
| V10 | O12→O13→O14 | 재현·일관된 backup/restore·모드·최종 증거 |

각 카드의 자세한 선행은 [매핑](feature-map.md)의 표를 따른다. 묶음 명칭이 선행 게이트나 카드 내부 작업을 생략하지 않는다. 인프라8과 Linux8은 겹쳐 가동하지 않는다.

## 6. 충돌 방지와 변경 통합

주 에이전트는 배정마다 책임 행동·허용 인터페이스·소비자·배타 자원·기준선·미정 게이트·검증 수준을 선언한다. 파일 경로는 필요한 경우 충돌 방지용으로만 부가하며 카드 goal을 대신하지 않는다.

공유 정의 변경은 ‘필요한 의미→소비자 영향→시험→migration/복구’ 요청으로 받는다. 주 에이전트가 하나씩 적용하고 영향을 받는 Luna에 새 기준선과 재검증 범위를 알린다. 공통 DTO를 각자 복사하거나 동일 이름의 port를 서로 다르게 구현하지 않는다.

통합은 (1) 제출 결과/기준선 확인 (2) 책임 밖 변경 검사 (3) 단위·계약 검증 (4) provider/consumer 결합 (5) DB/프로세스/실호스트 수준에 필요한 시험 (6) 로그·원장·실제 상태 대조 (7) 준비도/완료와 다음 작업 기록 순으로 한다. 다른 담당자의 변경을 덮어쓰거나 자동 stash/reset으로 정리하지 않는다.

## 7. 중단·재배정·PMT

- 같은 주장을 되풀이하며 기다리지 말고, 차단된 입력 의미·원천·검증 부재·영향 범위를 보고한다. 가능한 독립 하위 행동을 구분한다.
- 인계 시 실행 중 프로세스·점유·실제 부작용·남은 자원을 확인한다. 강제 중단을 제품 Job 취소로 해석하지 않는다.
- PMT 기록·lock·공유 목록·상태 전파는 주 에이전트만 수행한다. 실제 위임 Item은 scope·완료 기준·verify를 갖춘 뒤 엔진의 delegate 기준으로 점유한다.
- 이 문서 작성 단계에서 미래 구현 Item을 완료하거나 제품 자원을 생성하지 않는다.
- 재개 시 현재 카드·계약 revision·실제 변경/시험·미검증·다음 소비자를 이어받는다. 단순 대화 요약만으로 실호스트 검증을 재사용하지 않는다.
